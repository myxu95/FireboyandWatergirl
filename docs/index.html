fwbridge

How Claude Code and Codex hand work to each other without losing track of the bill

fwbridge lets one coding agent (Claude Code or Codex) hand a task to the other and run it in the background. It watches what the worker spends, stops it when a limit is reached, and also reports what the delegating agent spends while it waits.

Behaviour and measurements on this page: Claude Code 2.1.322 and codex-cli 0.167.0, November 2026. Source: github.com/myxu95/FireboyandWatergirl.

Why it exists

A delegated task gets expensive in two places.

  • The worker. Every model call re-reads the whole conversation, so the input a long task consumes grows roughly with the square of its number of calls. Left alone, a task that keeps going can burn an extraordinary number of tokens, mostly as cache reads.
  • The host. Each time the delegating agent checks on the task, it makes a model call that re-reads its own context. Checking in every minute for an hour means sixty such calls.

fwbridge puts a supervisor between the two agents that keeps books on both sides and enforces hard limits on the worker.

Architecture: no daemon

Three kinds of processes cooperate through one directory per task.

  • Host: the agent that asks for work. Claude Code calls the fwb CLI from its shell. Codex uses the MCP server (fwb mcp) because its shell runs inside a sandbox that cannot start a networked worker.
  • Supervisor: one detached process per task. It starts the worker, reads its event stream, keeps the token books, enforces limits and writes state.json.
  • Worker: claude -p or codex exec, doing the actual task.

Life of a task

  1. Entry The CLI (cmd_run in cli.py) and the MCP server (_delegate in mcp_server.py) only parse arguments. Both call create_task in tasks.py, so the two front ends behave identically.
  2. Checks and registration create_task refuses to start a task when:
    • the caller is itself running inside a delegated task, which would let the two agents bounce work back and forth;
    • another task is already running in the same directory;
    • the options do not fit the worker (only Claude Code reports cost, for example).
    For a follow-up (--resume) it looks up the earlier task's worker session and the usage that session had already accumulated. It records which agent session is the host, then writes task.json (the immutable request), prompt.txt and a queued state.json.
  3. Detach spawn_supervisor starts python -m fwbridge.supervisor <task dir> in its own session, and the command returns the task id at once.
  4. Supervise Supervisor.run in supervisor.py puts a fixed preamble in front of the prompt: work autonomously, do not delegate, stop and say so when blocked, report only what was verified. _run_worker asks the worker's adapter for the command line and starts the worker in its own process group. A reader thread queues its stdout lines, and once per second the loop:
    • hands each event to the adapter, which updates the token books;
    • lets the adapter read side channels (the Codex session file);
    • checks the limits, and on a breach kills the whole process group and marks the task killed;
    • writes state.json every two seconds.
  5. Finish A task ends with two layers of result:
    • status (succeeded, failed or killed) is what happened to the process;
    • outcome (completed, partial, blocked or failed) is the worker's own verdict, taken from its structured report.
    A partial outcome with rounds left starts a fresh session seeded with the previous report. Then result.md and result.json are written, the final state is published, and the notification command runs.
  6. Read back status, wait, result and log only read files. wait_task re-reads state.json once a second and makes no model calls, so a host blocked in fwb wait spends nothing. If the supervisor dies, load_state sees that its process is gone and reports the task as orphaned; fwb kill cleans up.

Worker adapters

Everything specific to one CLI lives in its adapter under workers/. Each implements the same small interface: build_command, on_event, poll, finalize and prepare. The supervisor never needs to know which worker it is running. Every rule below was established against recorded output of the real CLIs, which the tests replay.

Claude Code

claude -p --output-format stream-json

  • One model call is streamed as several events that repeat the same message id, so calls are deduplicated by id.
  • Streamed output counts run low, and compaction calls are not streamed at all. The final result event's totals are authoritative.
  • Structured result through --json-schema, cost from total_cost_usd, budget through --max-budget-usd.

Codex

codex exec --json

  • The stdout stream reports usage only once, when the turn ends.
  • Live per-call usage comes from the session file Codex writes under ~/.codex/sessions, which the adapter follows as it grows.
  • Structured result through --output-schema, compaction threshold through model_auto_compact_token_limit.

Both CLIs report a resumed session's usage as a running total since the session began. The adapters record the total before resuming and subtract it, so a follow-up task is charged only for its own calls.

Tokens and long tasks

Each model call is recorded as four parts: uncached input, cache read, cache write and output. The first three add up to the call's context, which is everything the model had to read. Context size is what drives runaway cost, so it is the quantity fwbridge watches most closely. Control comes in three layers, from soft to hard:

  1. Autocompaction (default 120,000 tokens). The worker summarises its own history and carries on.
  2. Context limit (default 200,000 tokens). If compaction does not keep up, the task is stopped.
  3. Backstops. Total tokens (10 million), model calls (200), cost (Claude Code only, off by default), silence (20 minutes) and wall time (4 hours). The status shows a warning at 80% of any limit.

Two ways to continue work that did not finish:

  • --max-rounds N starts fresh sessions that carry only the previous round's report. It is cheap, but the new session knows only what that report says.
  • --resume TASK reopens the same worker session. The worker remembers everything, and pays to re-read all of it.

The host side

When a task is created, fwbridge records which agent session asked for it. fwb status then reports that session's model calls and tokens during the task, next to the worker's.

  • Claude Code passes CLAUDE_CODE_SESSION_ID to its child processes, which leads to the session transcript under ~/.claude/projects.
  • Codex has no such variable. fwbridge walks up the process tree to the Codex process and finds the session file it holds open.

The Codex wake-up problem

Codex 0.167 calls MCP tools from a JavaScript cell that hands control back to the model after 30 seconds. The model then checks again about once a minute, and every hand-back is a full model call. In one measurement a single five-minute wait cost seven model calls. fwbridge counters this in two ways:

  • The MCP task_wait tool has no timeout argument. Given one, the model chose 50-second waits.
  • Its description, and the reply to delegate, tell Codex to begin the cell with // @exec: {"yield_time_ms": …}, so the cell stays blocked for the whole wait.

A stand-in worker played the task so that only host calls were counted. The whole delegation includes starting the task, reading the result and the final reply. With Claude Code as host and a blocking fwb wait, the measured host calls during the task were zero.

Guards

  • No nested delegation. Delegating from inside a task is refused, through the CLI and through MCP alike. Detection looks for an fwb supervisor among the caller's ancestor processes, because agent CLIs filter the environment they pass to tools and MCP servers.
  • One task per directory, so two agents never edit the same tree at once (--allow-concurrent overrides).
  • No permission-skipping defaults. Claude Code runs with acceptEdits, Codex with the workspace-write sandbox, unless the caller asks otherwise.
  • Notifications stay out of MCP. A notification command runs as a shell command outside any sandbox, so only the CLI and the FWB_NOTIFY_CMD variable can set one.
  • Reports are claims. The structured report is the worker's own account, and the host should check whatever matters.

On disk

Each task is a directory under ~/.local/state/fwbridge/tasks/ (or $FWB_HOME/tasks/):

task.json         the request; never changes
prompt.txt        the prompt as given
worker_input.txt  what the worker actually received (preamble + prompt)
state.json        live state, written only by the supervisor
events.jsonl      the worker's raw event stream
usage.jsonl       one line per model call
stderr.log        the worker's stderr
result.md         final report, readable form
result.json       final report, structured

Reading the code

  1. tasks.py shows how a task is created and how its state is read. This is the whole flow in one file.
  2. supervisor.py holds the run loop and the round logic.
  3. workers/claude.py pairs best with tests/test_adapters.py, which replays recorded streams and shows what each parsing rule handles.
  4. The outer layers can wait until needed: mcp_server.py, host.py and report.py.

Setup, every option and the full list of verified scenarios are in the README.
